---
title: Encryption at rest
description: AES-256-GCM encryption for sensitive database fields, and how to protect the key.
---

OpenAudioHub encrypts sensitive fields in the database with AES-256-GCM. The key comes from the `ENCRYPTION_KEY` environment variable, which the app requires at startup.

This is envelope encryption with a key held by the server. It is not zero-knowledge. The server needs the key to run transcription and summaries on your content.

## What is encrypted

| Column | Contents |
| --- | --- |
| `recordings.filename` | Recording titles, which often include generated topics |
| `transcriptions.text` | The full transcript |
| `ai_enhancements.summary` | The summary |
| `ai_enhancements.key_points` | Key points, stored as a versioned envelope |
| `ai_enhancements.action_items` | Action items, stored as a versioned envelope |
| `user_settings.summary_prompt` | Summary prompts, which can contain context about you |
| `user_settings.title_generation_prompt` | Title prompts |
| `plaud_connections.bearer_token` | The Plaud access token |
| `api_credentials.api_key` | Your AI provider API keys |
| `webhook_endpoints.url` | Webhook target URLs |
| `webhook_endpoints.secret` | Webhook signing secrets |

Search over transcripts is not implemented, so encrypting transcript text does not remove any feature.

### Outside the scope of this layer

- **Audio files,** in local storage or S3. For S3, enable bucket-level server-side encryption. Per-object encryption is not implemented.
- **Postgres data files on disk.** Use full-disk encryption on the host, or a managed database that encrypts storage.
- **Backups created by the export tool.** The ZIP from **Settings → Export/Backup** is plaintext, because it is meant for you to read and move. Store it as carefully as an unencrypted database.

## What this protects against

- Stolen database backups or snapshots.
- Read-only database access without access to the application server.
- A SQL injection that can read data but cannot run application code.
- Operators who can query the database but do not have the key.

## What this does not protect against

- **A compromised application server.** The server holds the key and decrypts content when it runs AI on it.
- **A compromised `ENCRYPTION_KEY`.** Treat the key like the master credential for your database.
- **Your AI provider.** Plaintext audio and transcripts go to the provider you configured, and this layer does not change that. To keep them on your own hardware, run a local provider such as Ollama or LM Studio on the same machine.

## Key management

`ENCRYPTION_KEY` must be exactly 64 hex characters, which is 32 bytes. Generate one with:

```bash
openssl rand -hex 32
```

Losing the key makes the encrypted content unrecoverable. Store a copy separately from your database backups, in a place with restricted access.

## Versioning

New ciphertext has a `v1:` prefix that names the format version. The reader also accepts older formats, and it returns any value that is not encrypted unchanged. That lets data written before encryption was enabled keep working until it is re-encrypted.

Key rotation is not implemented yet. The version prefix leaves room for a future rotation that can find the rows that need re-encryption.

## Backfilling existing rows

Rows written before encryption was enabled stay in plaintext until they are rewritten. To encrypt them, run the bundled script. It is idempotent, batched, and safe to interrupt and resume.

```bash
# Report what would change, without writing anything
docker compose exec app bun encrypt-backfill.js --dry-run

# Apply the changes
docker compose exec app bun encrypt-backfill.js
```

When you run from a source checkout, use `bun scripts/encrypt-backfill.ts` instead.
