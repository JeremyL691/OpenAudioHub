This page gives the overall picture. The column-level details are in [Encryption at rest](./encryption-at-rest).

## Authentication

There are two ways to authenticate to OpenAudioHub's HTTP surface.

1. **Browser session.** Better Auth signs you in with email and password. The session cookie is signed with `BETTER_AUTH_SECRET`. The interface and its internal API use sessions.
2. **Personal API key.** Starts with `oah_`. Keys created before version 1.0.0 start with `op_`, and both work. Sent as a Bearer token, and read-only. External tools use keys to call `/api/v1/*`.

Rate limits count requests per client IP. If your instance sits behind a reverse proxy, set `RATE_LIMIT_TRUST_PROXY_HEADERS=true` only when the proxy overwrites `X-Forwarded-For`. Otherwise clients can forge the header, and the limits stop working.

## Encryption at rest

Sensitive fields are encrypted with AES-256-GCM under `ENCRYPTION_KEY`, a 64-character hex key. The list of fields is in [Encryption at rest](./encryption-at-rest).

## API key hashing

Personal API keys are stored as HMAC-SHA256 hashes, never as plaintext. The HMAC key is `API_TOKEN_HASH_SECRET` when it is set, and `BETTER_AUTH_SECRET` otherwise. A database breach does not reveal usable keys, because an attacker would also need the HMAC key from the runtime environment.

Two consequences matter:

- Keys are not hashed with plain SHA-256. A random key is strong, but a plain hash would still allow precomputed lookups over the key space.
- `ENCRYPTION_KEY` is never used as the HMAC key. It is reserved for encryption.

## Webhook signatures

Each webhook delivery is signed:

- Header: `X-OpenAudioHub-Signature: t=<unix time>,v1=<hex HMAC>`
- Algorithm: HMAC-SHA256 over `<timestamp>.<raw body>`, using the endpoint's `whsec_` secret.
- Replay window: five minutes.

Receivers must compare signatures in constant time. The [automation guide](/docs/guides/automation-and-webhooks) has a reference implementation.

## Webhook target hardening

By default, a webhook URL can use `http://` or `https://`, and it can point at any address the OpenAudioHub container can reach. That includes Docker service names, private IP addresses, and public hosts. URLs with embedded credentials are rejected.

If other people can reach your instance, set `WEBHOOKS_REQUIRE_PUBLIC_TARGETS=true`. Then webhook URLs must use HTTPS, must resolve to public addresses, and must not contain credentials. Loopback, private, link-local, unique-local, multicast, and documentation addresses are rejected. This stops your instance from being used as a relay into your private network.

## Per-user query isolation

Every database query that touches user data includes `where(eq(table.userId, session.user.id))`. Routes under `/api/v1/*` take the user from the API key, and the rest take it from the session. Either way, the same user-scoped queries run.

## Account suspension

A suspended account is rejected before any feature code runs. Suspension is recorded in the `users.suspended_at` column. Session requests and API key requests both check it. There is no interface for suspending accounts yet, so an operator sets the column in the database.

## Trust boundaries outside OpenAudioHub

Some risks sit outside the application, and this page names them rather than claim to cover them.

- **Your AI provider.** Plaintext audio and transcripts go to the provider you configured. Its policies and infrastructure determine their privacy. If you do not trust the provider, run a local one on the same machine.
- **A compromised application server.** The server holds `ENCRYPTION_KEY` and decrypts content when it needs to. Encryption at rest protects against database breaches, not against code execution on the server.
- **A compromised `ENCRYPTION_KEY`.** Treat it like a database master credential. If it is lost, the encrypted content cannot be recovered.

## Compliance

OpenAudioHub does not claim HIPAA, SOC 2, or attorney-client privilege. Those claims depend on your AI provider, which may have its own certifications, and on how you deploy and operate your instance.

## Reporting a vulnerability

Report security issues privately through [GitHub's vulnerability reporting](https://github.com/JeremyL691/OpenAudioHub/security/advisories/new). The [security policy](https://github.com/JeremyL691/OpenAudioHub/blob/main/SECURITY.md) describes what to include.
