OpenAudioHub is a Next.js application backed by Postgres. The web interface, the API, and the background workers run in one process. The optional audio pipeline runs as a second container with a private API. Horizontal scaling means running more copies of the app behind a load balancer.

## Runtime

- **Web, API, and workers.** One Next.js process serves the interface and the API. The sync worker, transcription jobs, webhook deliveries, and export jobs run as background tasks inside that process.
- **Postgres.** The only required stateful dependency. Better Auth stores sessions there, and Drizzle ORM handles everything else.
- **Storage.** The local filesystem or an S3-compatible bucket holds audio files only. Metadata lives in Postgres.
- **AI providers.** External HTTPS endpoints that the app calls with the credentials you configured.
- **Audio pipeline (optional).** A FastAPI service with SQLite state, reachable only on the Compose network. It prepares long recordings. See below.

## Sync is pull-based

Plaud has no push interface, so OpenAudioHub pulls from it. The sync routine in `src/lib/sync/sync-recordings.ts` runs in two places: a background worker in `src/lib/sync/worker.ts` for every connected account, and the open browser tab.

1. List recordings from the connected Plaud account, one page at a time.
2. Compare each recording with the database. New recordings are inserted, changed ones are updated, and unchanged ones are skipped.
3. Download the audio once for each new recording, and hand it to the configured storage backend.
4. Emit `recording.synced` to subscribed webhooks.

The routine is idempotent. An interrupted run resumes on the next pass without duplicating anything.

## Pluggable storage

`StorageProvider` in `src/lib/storage/types.ts` is the interface. It has `uploadFile`, `downloadFile`, `getSignedUrl`, `deleteFile`, and `testConnection`. Two adapters ship: local and S3. The factory in `src/lib/storage/factory.ts` selects one from the instance configuration. Feature code never branches on the storage type.

## Pluggable AI

Most providers are OpenAI-compatible. The OpenAI SDK is configured with each provider's base URL, so the same calls reach OpenAI, Groq, Together AI, OpenRouter, LM Studio, Ollama, and any other compatible endpoint. Google Gemini and ElevenLabs have their own clients.

Transcription uses one of these styles, selected by the provider preset in `src/lib/ai/provider-presets.ts`:

- **OpenAI-style:** `POST /v1/audio/transcriptions` with the audio uploaded as a file.
- **Chat-style:** `POST /v1/chat/completions` with the audio as an input content part. OpenRouter uses this for audio-capable models.
- **Gemini and ElevenLabs:** their native speech APIs.

Adding a provider that needs non-standard authentication means writing an adapter behind an OpenAI-compatible surface. Do not branch on provider names in feature code.

## Long-audio pipeline

The pipeline handles recordings that are too long to send to a provider in one request. It runs as a separate container.

1. The pipeline decodes the recording with FFmpeg into 16 kHz mono PCM on disk.
2. Silero VAD finds the speech. Long silences are skipped, and the remaining speech is cut into continuous, non-overlapping chunks. Cuts prefer pauses near two minutes.
3. For each chunk, the app makes the provider request with its stored credentials and saves the result, encrypted, with timestamps restored to the original recording.
4. The pipeline keeps its job state and checkpoints in SQLite. A restart or a failed chunk resumes from the last completed chunk without repeating finished work.

Only the app holds provider credentials. The pipeline has no route to the internet, and it is reachable only on the Compose network. Details are in [docs/audio-pipeline.md](https://github.com/JeremyL691/OpenAudioHub/blob/main/docs/audio-pipeline.md).

## Routes

- `src/app/(app)/`: signed-in pages, including the overview, the recordings library, and settings.
- `src/app/(auth)/`: sign-in, registration, and password pages.
- `src/app/(docs)/`: this documentation site.
- `src/app/api/`: session-authenticated routes that the interface uses.
- `src/app/api/v1/`: the public, key-authenticated read API. See [Public API](./public-api).

## Multi-process safety

Background workers can run in several app processes against the same database. The sync worker, transcription jobs, and webhook worker claim work in the database with `SELECT ... FOR UPDATE SKIP LOCKED`. In-memory flags are only advisory. The default Compose file runs one app container, but the code does not depend on that.
