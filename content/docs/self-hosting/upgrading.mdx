---
title: Upgrading
description: Pull a new image, restart the stack, and choose the right tag for your risk tolerance.
---

OpenAudioHub publishes Docker images to GitHub Container Registry. An upgrade is an image pull and a restart. The app applies pending database migrations when its container starts, before it accepts requests.

## Standard upgrade

From the directory that holds your `docker-compose.yml` and `.env`:

```bash
docker compose pull && docker compose up -d
```

If a release changes the audio pipeline, its release notes say whether to start the pipeline first. Starting `audio-pipeline` before `app` is always safe:

```bash
docker compose pull && docker compose up -d audio-pipeline && docker compose up -d app
```

Migrations never run in a separate container. If a migration fails, the app does not start, and the logs show why.

## Picking a tag

`OPENAUDIOHUB_VERSION` in your `.env` selects the image tag that Compose pulls.

| Tag | What you get | Use when |
| --- | --- | --- |
| `latest` | The newest stable release | Most installations |
| `1.0.0`, `1.0` | A specific release, or a minor line | Production, when you want repeatable installs |
| `dev` | A build of `main` | Testing unreleased changes. Expect occasional breakage. |

`main` is the only long-lived branch and it can be broken at any commit. Deploy from tagged releases. Do not build production images from `main`. See [BRANCHING.md](https://github.com/JeremyL691/OpenAudioHub/blob/main/BRANCHING.md).

## Update notice

The footer shows an "Update available" notice when GitHub has a newer release. The notice does not install anything. The app checks GitHub once per session. To stop those checks, set `DISABLE_UPDATE_CHECK=true` in `.env`.

## Rolling back

To return to an earlier release, set `OPENAUDIOHUB_VERSION` to that tag, then run the upgrade command again:

```bash
docker compose pull && docker compose up -d
```

Migrations are additive by default, so an older image can usually run against a newer schema. A release that drops data says so in its changelog, and you should read those notes before you roll back across it.

Migration `0041_rebrand_source_values` rewrites stored transcript source values. If you roll back to a build from before that migration, run the SQL in the [migration guide](https://github.com/JeremyL691/OpenAudioHub/blob/main/docs/MIGRATION_FROM_RIFFADO.md#rollback) first.

## What to back up before an upgrade

Back up these before any major upgrade:

1. The database volume, `openaudiohub_pgdata` by default. Or take a logical dump with `pg_dump`.
2. The audio volume, `openaudiohub_audio`, if you use local storage. If you use S3, back up the bucket.
3. The pipeline data volume, `openaudiohub_audio-pipeline-data`, if the pipeline is enabled.
4. Your `.env` file, and a copy of `ENCRYPTION_KEY` stored separately from the database.

For a portable copy of your content, use **Settings → Export/Backup**. The ZIP it produces is plaintext, so store it as carefully as an unencrypted database. See [Backup and restore](/docs/guides/backup-and-restore).
